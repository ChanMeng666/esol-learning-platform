# Component Placement Guidelines

**Last Updated**: 2025-10-27
**Version**: 1.0

## Overview

This document defines the organizational structure for React components in the NZCEL ESOL Learning Platform. Following these guidelines ensures consistency, maintainability, and prevents component duplication.

## Directory Structure

```
src/
├── components/           # Reusable components
│   ├── ui/              # shadcn/ui primitives (DO NOT MODIFY)
│   ├── shared/          # Shared across entire app
│   ├── dashboard/       # Dashboard-specific widgets
│   ├── charts/          # Generic, reusable chart components
│   ├── practice/        # Practice module components
│   ├── conversation/    # Conversation module components
│   ├── speaking/        # Speaking module components
│   ├── audio/           # General audio utilities
│   ├── auth/            # Authentication components
│   ├── navigation/      # Navigation components
│   ├── layout/          # Layout components
│   ├── copilot/         # CopilotKit integration
│   ├── filters/         # Filter components
│   ├── data-table/      # Data table components (TanStack Table)
│   ├── calendar/        # Calendar components
│   └── spreadsheet/     # Spreadsheet components
├── app/
│   └── (dashboards)/
│       └── components/  # Dashboard-shared components only
└── lib/                 # Configuration & utilities
```

## Component Placement Rules

### 1. UI Components (`src/components/ui/`)

**Purpose**: shadcn/ui primitive components

**Rules**:
- ✅ Generated by `npx shadcn@latest add [component]`
- ❌ **NEVER** manually edit these files
- ❌ **NEVER** place custom components here
- ✅ Import and compose in higher-level components

**Examples**: `button.tsx`, `card.tsx`, `dialog.tsx`, `input.tsx`

---

### 2. Shared Components (`src/components/shared/`)

**Purpose**: Components used across multiple unrelated features

**Rules**:
- ✅ Generic, highly reusable components
- ✅ No feature-specific logic
- ✅ Configurable via props
- ❌ No direct data fetching (accept data via props)

**Examples**:
- `empty-state.tsx` - Generic empty state display
- `loading-state.tsx` - Generic loading indicators
- `error-boundary.tsx` - Error handling wrapper

**When to use**: Component is used in 3+ different feature areas

---

### 3. Dashboard Components (`src/components/dashboard/`)

**Purpose**: Dashboard-specific widgets and visualizations

**Rules**:
- ✅ Self-contained dashboard widgets
- ✅ May use Zustand stores internally
- ✅ Dashboard tab components
- ❌ Not for general-purpose components

**Examples**:
- `nzcel-tab.tsx` - NZCEL progress tab
- `general-practice-tab.tsx` - General practice tab
- `stat-card.tsx` - Dashboard statistics card
- `skill-radar-chart.tsx` - **Self-contained** chart (uses `useUserProgress()` hook)
- `progress-line-chart.tsx` - **Self-contained** chart (uses `useUserProgress()` hook)

**Naming Convention**: `[feature]-tab.tsx` for tab components

---

### 4. Charts Components (`src/components/charts/`)

**Purpose**: Generic, reusable chart components

**Rules**:
- ✅ Accept data via props (no internal data fetching)
- ✅ Configurable appearance and behavior
- ✅ Can be used anywhere in the app
- ❌ No Zustand store dependencies
- ❌ No feature-specific logic

**Examples**:
- `skill-radar-chart.tsx` - **Reusable** radar chart (accepts `data` prop)
- `progress-line-chart.tsx` - **Reusable** line chart (accepts `data` prop)
- `chart-revenue.tsx` - Revenue chart component
- `chart-visitors.tsx` - Visitor statistics chart

**Key Difference from Dashboard Charts**:
| Aspect | Dashboard Chart | Generic Chart |
|--------|----------------|---------------|
| Data Source | Internal (hooks) | External (props) |
| Usage | Dashboard only | Anywhere |
| Props | Minimal | Rich configuration |
| Example | `<SkillRadarChart />` | `<SkillRadarChart data={skillData} />` |

---

### 5. Feature-Specific Components

#### Practice Components (`src/components/practice/`)

**Purpose**: Practice module UI components

**Examples**:
- `question-card.tsx` - Question display card
- `listening-question-card.tsx` - Listening-specific questions
- `audio-player.tsx` - **Practice-specific** audio player (supports transcripts)
- `voice-recorder.tsx` - Voice recording component

**Rule**: If used exclusively in `/practice` routes, place here

---

#### Audio Components (`src/components/audio/`)

**Purpose**: General audio playback utilities

**Examples**:
- `audio-player.tsx` - **General** audio player (basic playback only)

**Key Difference from Practice Audio Player**:
| Feature | Practice Audio Player | General Audio Player |
|---------|---------------------|---------------------|
| Transcript Support | ✅ Yes (`showTranscript`, `transcript` props) | ❌ No |
| Use Case | Practice questions | History, cache display |
| Location | `practice/` | `audio/` |

---

### 6. Dashboard-Shared Components (`src/app/(dashboards)/components/`)

**Purpose**: Components shared across ALL dashboard layouts

**Rules**:
- ✅ Only components used by dashboard layouts
- ✅ Navbar, sidebar, header components
- ❌ Feature-specific components go in `src/components/[feature]/`

**Examples**:
- `app-sidebar.tsx` - Dashboard sidebar (used by all 6 dashboards)
- `dashboard-header-v2.tsx` - Enhanced dashboard header
- `nav-main.tsx` - Main navigation component
- `nav-user.tsx` - User profile navigation
- `theme-switcher.tsx` - Theme toggle component

**Naming Convention**: Avoid `-v2` suffixes in new code (explained in Anti-Patterns section)

---

### 7. Configuration Files (`src/lib/`)

**Purpose**: Application-level configurations

**Examples**:
- `dashboard-configs.ts` - Dashboard navigation configs
- `openai.ts` - OpenAI client configuration
- `stack.ts` - Stack Auth configuration
- `utils.ts` - Utility functions

**Rules**:
- ✅ Pure functions and constants
- ✅ No React components
- ❌ No `-v2` suffixes (use proper versioning)

## Decision Tree: Where Does My Component Go?

```
Is it a shadcn/ui component?
├─ YES → src/components/ui/ (generated, don't edit)
└─ NO
   ├─ Is it used across 3+ different features?
   │  ├─ YES → src/components/shared/
   │  └─ NO
   │     ├─ Is it dashboard-specific AND self-contained?
   │     │  ├─ YES → src/components/dashboard/
   │     │  └─ NO
   │     │     ├─ Is it a reusable chart (accepts data prop)?
   │     │     │  ├─ YES → src/components/charts/
   │     │     │  └─ NO
   │     │     │     ├─ Is it specific to practice module?
   │     │     │     │  ├─ YES → src/components/practice/
   │     │     │     │  └─ NO
   │     │     │     │     ├─ Is it specific to speaking module?
   │     │     │     │     │  ├─ YES → src/components/speaking/
   │     │     │     │     │  └─ NO
   │     │     │     │     │     └─ Is it used by all dashboard layouts?
   │     │     │     │     │        ├─ YES → src/app/(dashboards)/components/
   │     │     │     │     │        └─ NO → Create new feature folder in src/components/
```

## Anti-Patterns to Avoid

### ❌ 1. Version Suffixes (`-v2`, `-new`, `-old`)

**Bad**:
```
src/lib/dashboard-configs.ts
src/lib/dashboard-configs-v2.ts
src/components/dashboard/overview-tab.tsx
src/components/dashboard/overview-tab-new.tsx
```

**Why it's bad**:
- Creates confusion about which version to use
- Accumulates technical debt
- Hard to track what changed

**Good**:
- Delete old version when new one is stable
- Use git history to track changes
- If both are needed, give them descriptive names:
  ```
  dashboard-header-simple.tsx
  dashboard-header-with-search.tsx
  ```

---

### ❌ 2. Duplicate Components in Different Locations

**Bad**:
```
src/components/tables/data-table.tsx
src/components/data-table/data-table.tsx
```

**Why it's bad**:
- Wastes bundle size
- Maintenance nightmare (which one to update?)
- Import confusion

**Good**:
- One canonical location per component
- Use re-exports if needed for backward compatibility

---

### ❌ 3. Wrong Component Type in Folder

**Bad**:
```
src/components/ui/custom-widget.tsx          # Custom component in ui/
src/components/shared/nzcel-specific.tsx     # Feature-specific in shared/
src/app/(dashboards)/components/chart.tsx     # Reusable chart in dashboards/
```

**Why it's bad**:
- Breaks organizational logic
- Hard to find components
- Wrong assumptions about reusability

**Good**:
- Follow the decision tree above
- When in doubt, start more specific, refactor to shared later

---

### ❌ 4. Mixing Concerns

**Bad**:
```typescript
// audio-player.tsx - tries to be both general AND practice-specific
export function AudioPlayer({
  audioUrl,
  showTranscript,  // Only for practice
  enableCache      // Only for general
}) {
  // Too many if/else branches for different use cases
}
```

**Why it's bad**:
- Component becomes bloated
- Hard to maintain
- Props don't make sense for all use cases

**Good**:
- Separate components for different use cases
- Composition over configuration
- Clear, focused interfaces

## Special Cases

### 1. Similar Components with Different Purposes

**Scenario**: Two components that look similar but serve different purposes

**Example**:
- `components/dashboard/skill-radar-chart.tsx` - Self-contained, uses hooks
- `components/charts/skill-radar-chart.tsx` - Reusable, accepts props

**Decision**: Keep both, they serve different architectural patterns

**Documentation**:
```typescript
// components/dashboard/skill-radar-chart.tsx
/**
 * Self-contained Skill Radar Chart for Dashboard
 *
 * ✅ Use in: Dashboard tabs
 * ❌ Don't use in: Reusable contexts
 *
 * This component internally uses useUserProgress() hook.
 * For a reusable version, use components/charts/skill-radar-chart.tsx
 */
export function SkillRadarChart() { ... }

// components/charts/skill-radar-chart.tsx
/**
 * Reusable Skill Radar Chart
 *
 * ✅ Use in: Reports, comparisons, anywhere needing custom data
 * ❌ Don't use in: Simple dashboard tabs (use dashboard version instead)
 *
 * Requires data to be passed via props.
 */
export function SkillRadarChart({ data }: SkillRadarChartProps) { ... }
```

---

### 2. Empty State Components

**Scenario**: Generic empty state vs feature-specific empty state

**Decision**:
- `components/shared/empty-state.tsx` - Generic, configurable
- `components/history/empty-state.tsx` - Simplified interface for history feature

**Rule**: If the simplified version significantly improves DX for a specific feature, keep both

## Naming Conventions

### File Names
- **kebab-case**: `skill-radar-chart.tsx`
- **Descriptive**: Name describes what it does, not where it's used
- **No abbreviations**: `user-statistics-badge.tsx` not `user-stats-bdg.tsx`

### Component Names
- **PascalCase**: `SkillRadarChart`
- **Specific**: `ListeningQuestionCard` not `QuestionCard2`

### Function Names
- **Descriptive actions**: `getDashboardConfig()` not `getConfig()`
- **Verb-noun pattern**: `calculateProgress()`, `formatDate()`

## Migration Guide

### When You Find a Misplaced Component

1. **Verify it's truly misplaced** (use decision tree)
2. **Check all usages**:
   ```bash
   grep -r "from.*ComponentName" src --include="*.tsx"
   ```
3. **Move the file**:
   ```bash
   git mv src/components/old-location/component.tsx src/components/new-location/
   ```
4. **Update all imports**:
   ```bash
   # Update imports in all files
   find src -name "*.tsx" -exec sed -i 's|old-location/component|new-location/component|g' {} \;
   ```
5. **Test build**:
   ```bash
   npm run build
   ```
6. **Commit with clear message**:
   ```bash
   git commit -m "refactor(components): move ComponentName to correct location"
   ```

## Validation Checklist

Before creating a new component, ask:

- [ ] Is there already a similar component?
- [ ] Is this component truly reusable, or feature-specific?
- [ ] Does the location follow the decision tree?
- [ ] Is the interface clean and focused?
- [ ] Are there any version suffixes (-v2, -new)?
- [ ] Is the component documented with usage examples?

## Review Process

### When Adding New Components

1. **Check**: Does `src/components/[category]` exist for this type?
2. **If no**: Create new category with clear README
3. **Document**: Add JSDoc comments explaining purpose
4. **Review**: Have another developer verify placement

### When Reviewing PRs

1. **Component location makes sense**
2. **No duplicate components**
3. **No version suffixes**
4. **Follows naming conventions**
5. **Has proper TypeScript types**

## Cleanup Procedure

Periodically review for:

1. **Unused files**:
   ```bash
   # Find components not imported anywhere
   for file in src/components/**/*.tsx; do
     filename=$(basename "$file" .tsx)
     if ! grep -r "from.*$filename" src --include="*.tsx" --quiet; then
       echo "Unused: $file"
     fi
   done
   ```

2. **Version suffixes**:
   ```bash
   find src/components -name "*-v[0-9]*.tsx" -o -name "*-old.tsx" -o -name "*-new.tsx"
   ```

3. **Duplicate component names**:
   ```bash
   find src/components -name "*.tsx" -type f | \
     xargs -I {} basename {} | \
     sort | uniq -d
   ```

## Summary

### Key Principles

1. **One Source of Truth**: Each component has one canonical location
2. **Clear Boundaries**: Feature-specific vs reusable is well-defined
3. **No Versions**: Delete old code, use git history
4. **Document Exceptions**: If breaking rules, explain why in comments
5. **Refactor Proactively**: Move misplaced components immediately

### Quick Reference

| Component Type | Location | Key Characteristic |
|---------------|----------|-------------------|
| UI Primitives | `components/ui/` | shadcn/ui only |
| Shared Generic | `components/shared/` | 3+ features |
| Dashboard Widgets | `components/dashboard/` | Self-contained |
| Reusable Charts | `components/charts/` | Props-based |
| Feature-Specific | `components/[feature]/` | Single feature |
| Dashboard Layout | `app/(dashboards)/components/` | All dashboards |
